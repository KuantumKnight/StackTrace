STACKTRACE
Interactive CFG and Pushdown Automata Debugger
Detailed Project Concept

============================================================
1. PROJECT OVERVIEW
============================================================

Project Name:
StackTrace

Subtitle:
Visual Debugging for Context-Free Languages

Core Idea:
Build an interactive learning tool that combines Context-Free Grammars (CFGs)
and Pushdown Automata (PDAs) into one debugging environment.

Instead of only showing whether a string is accepted or rejected, the tool
should show exactly how the grammar or PDA works internally.

The project should allow students to:
- Define a CFG.
- Explore derivations.
- Visualize parse trees.
- Convert a CFG into a PDA.
- Design a PDA manually.
- Simulate PDA execution.
- Watch stack operations step by step.
- Explore nondeterministic execution branches.
- Understand why a string is accepted or rejected.
- Run test cases.
- Solve debugging challenges.

The distinguishing principle is:

"Every result should be explainable, reversible, and debuggable."

============================================================
2. WHY PUSH DOWN AUTOMATA IS A GOOD PROJECT
============================================================

A normal PDA simulator generally does this:

Input String -> ACCEPTED / REJECTED

That is not enough for a learning tool.

StackTrace should instead show:
- Current state.
- Remaining input.
- Stack contents.
- Transition taken.
- Input symbol consumed.
- Stack symbol popped.
- Symbols pushed.
- Alternative nondeterministic branches.
- Dead branches.
- Accepting branches.
- Complete execution history.

The user should be able to move backward and forward through execution like a
debugger in an IDE.

============================================================
3. BASIC PDA EXECUTION VISUALIZATION
============================================================

Suppose the PDA contains the transition:

delta(q0, a, Z) = (q0, AZ)

The tool should explain the transition visually.

Before transition:

State: q0
Input: aabb

Stack:
+---+
| Z |
+---+

Operation:
Read: a
Pop: Z
Push: AZ

After transition:

State: q0
Input: abb

Stack:
+---+
| A | <- TOP
+---+
| Z |
+---+

The interface should provide controls such as:

< Back
> Step
>> Run
Reset

The stack should animate whenever symbols are pushed or popped.

============================================================
4. NPDA EXECUTION TREE
============================================================

This should be one of the strongest features.

In a nondeterministic PDA, several transitions may be possible from the same
configuration.

For example:

Current configuration:

(q0, aabb, Z0)

Possible execution:

                    (q0, aabb, Z0)
                    /            \
                   /              \
              read a              epsilon
                 /                  \
        (q1, abb, AZ0)        (q2, aabb, Z0)
             /    \                 |
            /      \                X
          ...      ...             DEAD
           |
           OK
         ACCEPT

Each node represents:

(state, unread input, stack)

Branches should be categorized as:

ACTIVE
ACCEPTED
DEAD

When the student clicks a branch, show complete details.

Example:

Configuration #17

State:
q2

Remaining Input:
bb

Stack:
AAZ0

Transition Used:
delta(q1, b, A) -> (q2, epsilon)

Meaning:
- Read b
- Pop A
- Push nothing

This feature helps students understand nondeterminism much better than a static
state diagram.

============================================================
5. CFG TO PDA CONVERSION
============================================================

The most important integration in the project should be:

CFG -> PDA

Example grammar:

S -> aSb | epsilon

The tool should allow the student to click:

"Construct PDA"

Then explain the construction step by step.

Conceptual flow:

CFG
  |
  v
Push the start symbol
  |
  v
Replace variables using grammar productions
  |
  v
Match terminals with the input
  |
  v
Accept when the appropriate stack/input condition is reached

Example:

If S is on the stack and the grammar contains:

S -> aSb

Then the PDA can replace S with:

aSb

If the grammar contains:

S -> epsilon

Then S can be removed from the stack.

The tool should then allow the student to enter:

aaabbb

and watch how the PDA recognizes the same language generated by the CFG.

The conceptual lesson should be clear:

CFG describes how strings are generated.
PDA describes how strings are recognized using a stack.

============================================================

The CFG section should include:

6.1 CFG Editor
- Add productions.
- Edit productions.
- Set start symbol.
- Detect terminals.
- Detect non-terminals.
- Validate grammar syntax.

Example:

T -> T * F | F

6.2 Derivation Explorer

Allow students to choose:

LEFTMOST DERIVATION
RIGHTMOST DERIVATION
PARSE TREE

Example:

Grammar:
S -> aSb | epsilon

Input:
aaabbb

Leftmost derivation:

S
=> aSb
=> aaSbb
=> aaaSbbb
=> aaabbb

The replaced non-terminal should be highlighted at every step.

6.3 Parse Tree Visualization

Automatically generate a parse tree for successful derivations.

6.4 CFG Analysis

The tool may also include:
- Left recursion detection.
- Left recursion removal.
- Left factoring.
- FIRST set.
- FOLLOW set.
- Ambiguity witness search.

These make the CFG side much stronger.

8. ACCEPTANCE MODES
============================================================

Support both standard PDA acceptance methods:

1. Acceptance by final state
2. Acceptance by empty stack

The tool should allow the student to select the acceptance mode.

Example comparison:

Current PDA

aaabbb -> ACCEPTED

An advanced feature can show how constructions for the two acceptance modes are

10. WHY WAS THIS STRING REJECTED?
============================================================

Do not only show:

REJECTED

Instead provide a complete explanation.

Example:

Input:
aabbb

Result:
REJECTED

Explanation:

All 7 computation branches terminated.

Closest Branch:

State:
q1

Remaining Input:
b

Stack:
Z0

No transition exists for:

delta(q1, b, Z0)

The tool should highlight the missing or invalid transition in the state diagram.

This is one of the key "debugger" features.

11. LANGUAGE TEST BENCH
============================================================

Students should be able to define a PDA once and test multiple strings.

Example:

String        Result        Steps
-------------------------------------
epsilon       ACCEPTED      2
ab            ACCEPTED      5
aabb          ACCEPTED      8
aaabbb        ACCEPTED      11
aabbb         REJECTED      8
abb           REJECTED      6
abab          REJECTED      7

Allow students to write test assertions such as:

accept "aabb"
accept "aaabbb"
reject "aabbb"
reject "abab"

Then automatically execute all tests.

This makes the project feel like a programming/debugging tool.

============================================================
12. CHALLENGE MODE
============================================================

Challenge mode can make the project much more engaging.

Instead of always asking students to construct a PDA from scratch, give them
broken machines and ask them to debug them.

Example Challenge 1:

Expected Language:

L = { a^n b^n | n >= 1 }

Problem:

The current PDA incorrectly accepts:

aabbb

Task:

Find and repair the incorrect transition.

------------------------------------------------------------

Example Challenge 2:

Input:
aaabbb

Expected:
ACCEPT

Actual:
REJECT

Hint:
A required epsilon-transition may be missing.

------------------------------------------------------------

Example Challenge 3:

The PDA is getting stuck with one stack symbol remaining.

Task:
Find why the accepting transition is not being triggered.

------------------------------------------------------------

Challenge difficulty levels can be:

Level 1:
Basic stack operation

Level 2:
Missing transition

Level 3:
Incorrect stack push

Level 4:
Incorrect pop

Level 5:
Wrong acceptance condition

Level 6:
Nondeterministic branch problem

Level 7:
CFG-to-PDA conversion bug

13. PDA VS DFA LEARNING EXPERIMENT
============================================================

This feature can connect PDA concepts back to finite automata.

Example language:

L = { a^n b^n | n >= 0 }

Explain:

DFA:
Cannot recognize this language because it has only finite memory.

PDA:
Can recognize it using a stack.

Conceptually:

Read a -> PUSH
Read a -> PUSH
Read a -> PUSH

Read b -> POP
Read b -> POP
Read b -> POP

If input and stack conditions are satisfied:

ACCEPT

This demonstrates why the stack increases computational power.

18. INTERNAL PDA REPRESENTATION
============================================================

A PDA can be represented internally using structures such as:

State:
- id
- name
- initial
- accepting
- x coordinate
- y coordinate

Transition:
- from state
- to state
- input symbol
- required stack top
- replacement stack string

Configuration:
- current state
- input position
- current stack
- parent configuration
- transition used
- status

Status values:

ACTIVE
ACCEPTED
DEAD

For NPDA simulation, the engine should manage a set or queue of active
configurations.

============================================================
19. NPDA SIMULATION LOGIC
============================================================

Each configuration should be represented as:

(state, remaining input, stack)

For each active configuration:

1. Find all valid transitions.
2. Include transitions consuming the next input symbol.
3. Include epsilon-transitions.
4. Check the top of the stack.
5. Apply every valid transition.
6. Create one child configuration for every possible transition.
7. Continue exploring branches.
8. Mark a branch dead when no transition is possible.
9. Mark a branch accepted when the selected acceptance condition is satisfied.

To avoid infinite epsilon loops, the simulator should track visited
configurations.

A configuration key can include:

current state
input position
stack contents

The simulator can place reasonable limits on:
- Maximum number of configurations.
- Maximum execution depth.
- Maximum stack size.

If a safety limit is reached, the tool should report:

"Execution limit reached"

rather than incorrectly claiming rejection.

20. EXECUTION TRACE SYSTEM
============================================================

Every simulation step should create a trace event.

Example trace:

Step 1
State: q0
Input: aaabbb
Stack: Z

Transition:
a, Z -> AZ

Result:
State: q0
Input: aabbb
Stack: AZ

------------------------------------------------------------

Step 2
State: q0
Input: aabbb
Stack: AZ

Transition:
a, A -> AA

Result:
State: q0
Input: abbb
Stack: AAZ

The UI should be generated from these trace records.

This separation is important:

PDA Engine
   |
   v
Trace Events
   |
   v
Visualization

Do not directly mix simulation logic with animation logic.

============================================================
21. TIME-TRAVEL DEBUGGING
============================================================

Allow the user to move backward in the simulation.

Because every configuration is stored, the user can press:

< Previous

and return to an earlier configuration.

For nondeterministic simulation, selecting a node in the execution tree should
restore that branch's exact state.

This is a major differentiating feature.
